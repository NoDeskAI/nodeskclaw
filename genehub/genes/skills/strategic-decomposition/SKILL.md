# 战略拆解

当需要把目标变成可执行计划时，使用本方法：先澄清目标，再分解为阶段与任务，画出依赖与关键路径，并设计检查点。

## 目标澄清

拿到一个目标后，先不急着分解。先问清楚：

- **成功的样子是什么？** 具体、可衡量。不是「更好」，而是「指标 X 达到 Y」或「交付物 Z 通过验收标准 W」。
- **有什么硬性约束？** 时间、资源、技术、合规等不可突破的边界。
- **什么是必须的 vs 期望的？** 必须项不满足则失败；期望项可妥协。
- **谁是利益相关方？** 他们各自关心什么？验收权在谁？

澄清后再分解，避免拆了一堆「错误的问题」。

## 分解方法

- **目标 → 阶段**：按里程碑切分，每个阶段有可验证的交付物。阶段之间可以是顺序或部分并行。
- **阶段 → 任务**：每个任务是一个独立可执行单元，可分配给单人或单团队在有限时间内完成。

**任务描述六要素**（每个任务尽量包含）：

| 要素 | 内容 |
|------|------|
| 做什么 | 交付物或结果的精确描述。 |
| 为什么 | 在全局中的位置，便于执行者理解上下文。 |
| 成功标准 | 怎样算完成，可验证。 |
| 约束条件 | 必须满足的限制或不要做的事。 |
| 依赖项 | 依赖哪些其他任务或资源，何时可用。 |
| 预估工作量 | 粗估人天或复杂度，便于排期与负载均衡。 |

## 依赖图谱

- 哪些任务阻塞哪些任务？画出依赖关系（A 完成才能做 B）。
- **关键路径**：从开始到结束，依赖链最长的那条路径。关键路径上的延迟会直接拖累整体。
- 哪些任务可以并行？在无数据依赖和逻辑冲突的前提下，尽量并行以缩短总工期。

## 并行化策略

- 识别可并行的任务簇，安排不同执行者或不同时间段同时进行。
- 避免在未明确依赖时强行并行导致返工；依赖不清时先做少量串行或小批量验证。

## 检查点设计

在关键阶段（如阶段结束、关键路径节点）设立检查点。每个检查点定义「此时应为真的条件」：

- 例如：「所有接口契约已冻结」「性能基线已达标」「安全评审已通过」。

如果检查点不满足，意味着需要调整计划（加人、缩范围、延时间或改方案），而不是继续往下推。

## 应用原则

- **先澄清再分解** — 成功样子与约束不清就不动手拆。
- **任务要可执行** — 每个任务有清晰做什么、完成标准、依赖与边界。
- **依赖要显式** — 画出依赖与关键路径，避免隐藏瓶颈。
- **检查点要真** — 检查点不通过就触发调整，不是走形式。
