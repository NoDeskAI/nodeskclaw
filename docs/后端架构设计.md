Instance 表新增字段：
- `proxy_token` VARCHAR(64)，唯一索引，与 `OPENCLAW_GATEWAY_TOKEN` 同值。用于 OpenClaw Control UI / WebSocket 网关认证。
- `wp_api_key` VARCHAR(96)，唯一索引，格式 `nodeskclaw-wp-{64位hex}`。用于 LLM Proxy 认证，与 gateway token 分离。
- `llm_providers` JSONB（可空），存储该实例启用的 LLM Provider 列表（如 `["minimax-openai"]`），用于实例级 LLM 配置隔离。`sync_openclaw_llm_config` 按此字段过滤 `UserLlmConfig`，避免不同实例间配置互相泄漏。为 NULL 时回退到旧行为（读取用户在该组织下的全部配置）。
- `agent_label` VARCHAR(128)（可空），Agent 在工作区中的标签/子标签，描述该 Agent 的职责，与 `agent_display_name` 配合在工作区画布（2D/3D 视图）中展示。

### 软删除策略

所有模型均通过 `BaseModel` 继承 `deleted_at` 字段，采用逻辑删除：

- **删除操作**：设置 `deleted_at = now()`，不物理删除行
- **查询过滤**：所有 `select()` 查询必须加 `Model.deleted_at.is_(None)` 条件
- **级联逻辑删除**：删除集群时级联逻辑删除其下实例和部署记录；删除实例时级联逻辑删除部署记录
- **名称复用**：已逻辑删除的记录不占用名称唯一性，同名可重新创建
- **自动迁移**：升级到软删除版本后首次启动时自动为已有表添加 `deleted_at` 列和索引

```python
    code: int = 0              # 0=成功, 非0=失败
    error_code: Optional[int] = None      # 失败时必填，成功时为空
    message_key: Optional[str] = None     # 失败时必填，如 errors.auth.token_invalid
    message_params: Optional[dict] = None # i18n 插值参数，前端用于 t(message_key, message_params)
    message: str = "success"
    data: Optional[T] = None

class PageResponse(ApiResponse[T]):
    total: int = 0
    page: int = 1
    page_size: int = 20
```

**错误码规范**:

| 范围 | 模块 | 示例 |
|------|------|------|
| 10xxx | 认证 | 10001 Token 过期, 10002 无权限 |
| 20xxx | 集群 | 20001 连接失败, 20002 KubeConfig 无效 |
| 30xxx | 实例 | 30001 名称已存在, 30002 实例不存在 |
| 40xxx | 部署 | 40001 预检失败, 40002 资源创建错误 |
| 50xxx | 系统 | 50001 内部错误 |

**错误响应约定**:

- 只要出现 `error_code` 即表示失败响应
- 失败响应字段：`code` + `error_code` + `message_key` + `message` + `data`
- `message_params`（可选）：当 `message_key` 含插值参数时返回，前端用 `i18n.global.t(message_key, message_params)` 渲染
- 不再返回 `detail` 字段
- HTTP `status_code` 沿用当前实现，不改为统一 200

#### OAuth 登录组织匹配逻辑

`POST /auth/oauth/callback` 在换取用户信息后，额外执行租户匹配：

1. 通过 Provider Registry 获取对应 Provider（如 FeishuProvider），用 `code` 换取 `user_info` + `provider_tenant_id`
2. 创建或更新 `UserOAuthConnection`（user_id, provider, provider_user_id, provider_tenant_id）
3. 用 `provider_tenant_id` 查 `OrgOAuthBinding`（org_id, provider, provider_tenant_id）
   - **匹配到** → 自动创建 `OrgMembership`（role=member），设 `current_org_id` → `needs_org_setup=false`
   - **未匹配** → `needs_org_setup=true`，前端跳转 `/setup-org`

| 方法 | 路径 | 请求体 | 响应 data | 说明 |
|------|------|--------|-----------|------|

- 需要 JWT 认证（用户已登录）
- 从当前用户的 `UserOAuthConnection` 取对应 `provider` 的 `provider_tenant_id`（必须存在，否则 400）
- `job_title` 可选值：`founder` / `cto` / `engineer` / `pm` / `designer` / `ops` / `manager` / `other`
- **并发安全**：`OrgOAuthBinding` 唯一约束 `(org_id, provider, provider_tenant_id)`，插入冲突时改为查询已有组织并加入（role=member）

### 4.8 LLM Key 管理 `/api/v1/orgs` + `/api/v1/users`

#### 双通道模型

LLM Key 使用分为两种模式：

- **组织 Key（proxy 模式）**：用户选择后，请求经由 NoDeskClaw 的 `llm_proxy` 转发。Proxy 自动按 `(org_id, provider)` 查找管理员配置的 `org_llm_keys` 中首条可用 Key 进行调用。用户无需选择具体哪条 Key。`openclaw.json` 写入 proxy URL + `wp_api_key`（独立于 gateway token 的 LLM Proxy 专用认证 Key）。
- **个人 Key（直连模式）**：用户提供自己的 API Key，请求直接发往目标 Provider 的 base URL，不经过 proxy。`openclaw.json` 直接写入用户真实 API Key + Provider 默认 base URL。

### 4.9 LLM 代理（独立服务 `nodeskclaw-llm-proxy`）

LLM 代理已拆分为独立项目 `nodeskclaw-llm-proxy/`，独立部署到 K8s，通过私网域名供 OpenClaw 实例访问。后端 `nodeskclaw-backend` 中的 `llm_proxy.py` 仅在 `DEBUG=true` 时挂载，用于本地开发。

```
ANY    /:provider/*path            LLM 请求代理转发（仅组织 Key 模式使用）
```

使用 `instances.wp_api_key` 鉴权（独立于 gateway token），不依赖 JWT。兼容过渡期：若 `wp_api_key` 未匹配到实例，回退查 `proxy_token`。

流程：wp_api_key 查实例 -> user_llm_configs 查 Key 来源 -> 按 `(org_id, provider)` 自动查找首条可用 org_llm_key -> 额度检查 -> 流式转发 -> 记录 usage。

个人 Key 模式下请求不经过此代理，由 OpenClaw 直连目标 Provider。

支持的 Provider：OpenAI、Anthropic、Gemini、OpenRouter、Minimax-OpenAI、Minimax-Anthropic。认证头按类型区分：OpenAI/OpenRouter/Minimax 用 `Authorization: Bearer`，Anthropic 用 `x-api-key`，Gemini 用 URL 参数。

**部署架构**：LLM Proxy 以 FastAPI 服务运行在 K8s Pod 中，同 Pod 内运行 Clash sidecar 提供出站代理（访问 OpenAI/Anthropic 等外部 API）。通过私网 DNS 解析使 10 网段内的 OpenClaw Pod 可通过域名直达。后端写入 `openclaw.json` 时，组织 Key 的 `baseUrl` 按 API 类型区分：OpenAI 类指向 `{LLM_PROXY_URL}/{provider}/v1`，Anthropic 类指向 `{LLM_PROXY_URL}/{provider}`（不含 `/v1`，因为 Anthropic SDK 自行追加 `/v1/messages` 路径）。详细部署方案见 `docs/VKE部署方案.md` 第十节。

**Proxy Token 提取**：LLM Proxy 同时支持从 `Authorization: Bearer` 和 `x-api-key` 头提取 proxy token，以兼容 OpenAI SDK（Bearer）和 Anthropic SDK（x-api-key）的认证方式。

### 5.1 DeployService — 部署编排

整个部署流程是异步的，通过 `asyncio.create_task` 启动后台任务，前端通过 SSE `GET /stream/deploy/:id/progress` 接收进度。

```
DeployService.create_deploy(request) 流程:

  1. 参数校验 & 入库 (Instance + DeployRecord, status=in_progress)，同时将 llm_configs 中的 provider 列表保存到 instance.llm_providers
  2. 若 request.llm_configs 非空，upsert UserLlmConfig（按 user_id + org_id + provider）
  3. asyncio.create_task → _do_deploy(deploy_id)
  4. 立即返回 deploy_id 给前端

  │
  ├─ Step 1: 创建 Namespace + 隔离策略
  │  ├─ 创建 Namespace nodeskclaw-{name}（带管理标签，名称 RFC 1123 清洗）
  │  ├─ 创建 ResourceQuota（CPU/内存/Pod 数/存储上限）
  │  ├─ 创建 LimitRange（容器默认 limits 兜底）
  │  ├─ 创建 NetworkPolicy（网络隔离：禁止跨实例访问）

  │
  ├─ Step 2: 创建 K8s 资源（ConfigMap + Deployment + Service(ClusterIP) + Ingress(自动路由)）
  │  ├─ 调用 create_openclaw_instance(k8s, request, instance_id)
  │  │   ├─ kubernetes-asyncio 直接创建各资源
  │  │   ├─ Service 固定 ClusterIP，端口 18789
  │  │   └─ Ingress 自动生成 hostname: {name}.{ingress_base_domain}，含 TLS + WebSocket annotations
  │  └─ broadcast("deploy:{id}", {step: "create_resources", status: "done"})
  │
  ├─ Step 3: 轮询 Deployment 状态（最多 5 分钟）
  │  ├─ while not all_pods_ready:
  │  │   ├─ 查询 Deployment .status
  │  │   ├─ 计算 progress 百分比
  │  │   ├─ broadcast("deploy:{id}", {progress, pods_ready, pods_total})
  │  │   └─ await asyncio.sleep(3)
  │  └─ broadcast("deploy:{id}", {step: "pods_ready", status: "done"})
  │
  ├─ Step 4: 验证 Service / Ingress 可达
  │  └─ broadcast("deploy:{id}", {step: "service_ready", status: "done"})
  │
  ├─ Step 5（条件）: 应用实例配置
  │  ├─ 仅当 request.llm_configs 非空时执行
  │  ├─ ensure_openclaw_gateway_config + sync_openclaw_llm_config
  │  └─ broadcast("deploy:{id}", {step: "apply_config", status: "done"})
  │
  ├─ 成功: 更新 DeployRecord.status = success, Instance.status = running
  │  └─ broadcast("deploy:{id}", {status: "success", progress: 100})
  │
  └─ 失败: 更新 DeployRecord.status = failed, Instance.status = failed
     └─ broadcast("deploy:{id}", {status: "failed", error: message})
```

### 后台任务 Session 管理规范

通过 `asyncio.create_task()` 启动的后台任务 **不能** 复用请求作用域的 `db: AsyncSession`，因为请求结束后 FastAPI 的 `get_db` 依赖会关闭该 session。后台任务必须在内部通过 `async_session_factory()` 创建独立 session，并通过 ID 重新加载需要操作的数据库对象。

```python
# 正确：后台任务内部创建独立 session
async def _background_task(record_id: str) -> None:
    from app.core.deps import async_session_factory
    async with async_session_factory() as db:
        record = await db.get(Model, record_id)
        # ... 操作 ...
        await db.commit()

# 调用处只传 ID
asyncio.create_task(_background_task(record.id))
```

涉及此模式的模块：`deploy_service.py`（部署编排）、`gene_service.py`（基因学习任务）。

### Custom Skill 发现机制

OpenClaw 的 skill 加载分为两类：

- **Native skills**：内置于 OpenClaw 安装目录（`/usr/local/lib/node_modules/openclaw/skills/`），通过 `commands.nativeSkills: "auto"` 自动发现
- **Custom skills**：由基因学习写入 `/root/.openclaw/skills/<skill-name>/SKILL.md`，需要在 `openclaw.json` 中通过 `skills.load.extraDirs` 显式指定扫描目录

基因学习流程（`_direct_install`）和加入工作区流程（`deploy_nodeskclaw_channel_plugin`）都会调用 `openclaw_session.ensure_skills_discovery()` 确保 `openclaw.json` 包含：

```json
{
  "skills": {
    "load": {
      "extraDirs": ["/root/.openclaw/skills"]
    }
  }
}
```

使用绝对路径 `/root/.openclaw/skills` 而非相对路径，因为 OpenClaw 会将相对路径解析为相对于 workspace 目录（`/root/.openclaw/workspace/`），导致路径错误。

**SKILL.md 格式要求**：OpenClaw 的 `loadSkillFromFile` 要求 SKILL.md 必须包含 YAML front matter 中的 `name` 和 `description` 字段，否则 skill 不会被加载。`_write_skill_file` 会在内容缺少 front matter 时自动补全：

```yaml
---
name: <skill-name>
description: <gene.short_description>
---
```

**Session Snapshot 失效处理**：OpenClaw 在每个 session 中缓存一份 `skillsSnapshot`（含已发现的 skills 列表和格式化后的 prompt），存储在 Pod 上的 `sessions.json` 中。PVC 上的文件变化不会触发 OpenClaw 的 chokidar file watcher 自动刷新，已有 session 的 snapshot 永远不会自动更新。

因此，基因学习/遗忘后必须执行三步：

1. **`openclaw_session.invalidate_skill_snapshots(fs)`**：通过 kubectl exec 读取 `sessions.json`，清除所有 session 的 `skillsSnapshot` 字段后写回，使下次聊天时强制重建
2. **`openclaw_session.inject_evolution_notification(fs, gene_name, action)`**：通过 kubectl exec 向所有活跃 session 的 `.jsonl` 对话文件追加一对 user+assistant 消息（"你获取了新基因 X，完成了一轮进化"），防止 LLM 因对话历史中的旧 skill 列表而重复过时回答；同时将 `systemSent` 重置为 `false` 以强制下次对话重建 system prompt。注意：`systemSent` 定义在 OpenClaw 的 `SessionEntry` 类型中（`src/config/sessions/types.ts`），但读取逻辑在闭源的 `@mariozechner/pi-coding-agent` NPM 依赖中，OpenClaw 开源代码仅定义类型、不包含使用该字段的运行时逻辑。`sessionFile` 字段存储的是容器内绝对路径（如 `/root/.openclaw/.../xxx.jsonl`），PodFS 直接 strip `/root/` 前缀即可使用，无路径映射问题
3. **`restart_instance()`**：重启 Pod（scale 0→N），使 OpenClaw 进程重新加载 skill 文件

**对话历史污染问题**：仅清除 snapshot 不够——Pod 上的 `.jsonl` 对话文件保留了旧回复（如 Agent 说"我只有 3 个技能"）。新 Pod 启动后 LLM 看到历史消息中自己的旧回答，会直接复述而不重新检查 system prompt。通过注入进化通知消息，LLM 的对话上下文中包含了明确的 skill 变更确认，避免重复过时信息。

### 5.5 LlmConfigService — LLM 配置读写（kubectl exec）

LLM 配置不走 ConfigMap / env vars，直接读写 Pod 上的 `/root/.openclaw/openclaw.json`。

**读写方式**：通过 `kubectl exec` 逐文件操作（`nfs_mount.py` 中的 `PodFS` 类）。每次 `read_text`/`write_text` 都是对运行中 Pod 的一次 exec 调用，精确操作指定文件，无 NFS 挂载、无 temp dir、无批量同步。

```
读写流程（PodFS）:
  1. remote_fs(instance, db) 获取实例所在集群的 K8s 客户端
  2. 通过 label selector 找到 Running Pod 和容器名
  3. PodFS.read_text(path) → exec: cat /root/{path}
  4. PodFS.write_text(path, content) → exec: base64 -d > /root/{path}（自动 mkdir）
  5. 无挂载/卸载，无缓存，每次操作独立

典型 LLM 配置同步 = 2 次 exec（1 read + 1 write）。
```

```
两条写入路径:

1. 门户保存路径（write_instance_llm_configs）:
   接收 InstanceLlmConfigItem 列表 → 按 key_source 构造 providers JSON → 直接写入 Pod

2. 部署初始化路径（sync_openclaw_llm_config，仅首次部署使用）:
   从 DB 读取 UserLlmConfig → 按 instance.llm_providers 过滤 → 构造 providers → 写入 Pod

read_instance_llm_configs(instance, current_user_id):
  1. PodFS 读取 openclaw.json → 解析 models.providers
  2. 推断 key_source（baseUrl 含 proxy host = org，否则 personal）
  3. 将 OpenClaw 模型格式转回存储格式（camelCase → snake_case）
  4. 查当前用户 UserLlmKey 补充 personal_key_masked

restart_openclaw(instance):
  1. kubectl exec kill -SIGTERM 1 优雅重启 OpenClaw（不再同步配置）
  2. 轮询 Pod Ready（或超时）
```

门户保存时直接写 Pod 文件，不经 DB 中间层。首次部署时仍通过 DB（sync_openclaw_llm_config），因为部署是异步流程，配置需要临时持久化。

**前提条件**：目标 Pod 必须处于 Running 状态。后端容器无需 SYS_ADMIN 权限或 NFS 工具。

**Gateway 配置保障（`_ensure_gateway_config`）**：

每次写入 `openclaw.json` 时自动校正 gateway 配置，确保反向代理场景下的关键字段正确：

| 字段 | 行为 | 说明 |
|------|------|------|
| `gateway.auth.token` | 强制设为 `instance.proxy_token` | Control UI / WebSocket 认证 |
| `gateway.trustedProxies` | 缺失时补为内网 CIDR | Ingress Controller IP 信任 |
| `controlUi.allowInsecureAuth` | 强制设为 `true` | 绕过设备配对（非 localhost 必需） |
| `controlUi.dangerouslyDisableDeviceAuth` | 强制设为 `true` | 跳过 device identity pairing（2026.3.x+ 新增的安全层，Ingress 反代场景必需） |
| `controlUi.dangerouslyAllowHostHeaderOriginFallback` | **版本感知**：仅当已存在时确保为 `true` | 新版 OpenClaw 要求非 loopback 绑定时配置 Origin 校验，由镜像 entrypoint 首次设置，后端仅做保留 |

版本感知策略：`dangerouslyAllowHostHeaderOriginFallback` 是新版 OpenClaw 引入的安全校验字段。旧版 schema 使用 `.strict()` 模式会拒绝未知字段。后端不主动添加该字段，避免旧版实例因 schema 校验失败而崩溃；新版实例的 entrypoint 在启动时已设置该字段，后端读取到后会保留。`dangerouslyDisableDeviceAuth` 无条件设置，旧版忽略未知字段不影响运行。

### 5.6 ChannelConfigService — Channel 配置（kubectl exec）

Channel 配置与 LLM 配置同理，直接读写 Pod 上的 `openclaw.json` 中的 `channels` 字段。

**核心能力**：

4. **自定义 Channel 部署**：支持三种来源 —— 项目仓库部署（PodFS 复制文件）、用户上传（tgz/zip）、npm 第三方（openclaw plugins install）

### 5.7 LLM 代理转发

LLM 代理仅服务于组织 Key 模式。个人 Key 模式下 OpenClaw 直连 Provider，不经过此代理。

```
LlmProxy 请求处理流程:
  1. Authorization: Bearer <wp_api_key> → 查 instances.wp_api_key（索引），未命中时回退查 proxy_token
  2. URL path 提取 provider → 查 user_llm_configs
  3. 按 (org_id, provider) 自动查找首条 active 的 org_llm_key → 额度检查
  4. 按 Provider 设置认证头 (bearer / x-api-key / query param)
  5. 注入 stream_options 确保流式响应含 usage
  6. httpx.AsyncClient 流式转发
  7. 解析响应 usage → INSERT llm_usage_logs
```

**上游请求必须剥离 `Accept-Encoding`**：`_build_auth_headers` 转发客户端请求头时，必须剥离 `accept-encoding`。Node.js 22 的 `fetch` 默认携带 `Accept-Encoding: gzip, deflate`，若原样转发给上游 LLM Provider，上游返回 gzip 压缩的 SSE 流，但 `httpx` 因该头非自身添加而跳过自动解压，`aiter_lines()` 遍历到压缩二进制导致客户端空回复。剥离后 `httpx` 自行管理压缩协商并自动解压。`_handle_stream` 另保留 `Cache-Control: no-transform` + `X-Accel-Buffering: no` 防止中间代理二次压缩。详见 `docs/VKE部署方案.md` 11.4 节。

## 六、SSE 实时推送设计

> 选择 SSE 而非 WebSocket 的原因：NoDeskClaw 的实时场景全部是服务端单向推送（日志、事件、进度、状态），客户端命令（订阅/暂停）用普通 REST 请求即可。SSE 更简单、HTTP 原生、自动重连、负载均衡零配置。

### 6.1 SSE 流端点

| 端点 | 用途 | 认证 | 参数 |
|------|------|------|------|
| `GET /stream/instances/:id/status` | 实例状态 + Pod 变更 | Bearer JWT | — |
| `GET /stream/instances/:id/events` | K8s 事件流 | Bearer JWT | `?type=Warning` |
| `GET /stream/instances/:id/logs` | Pod 实时日志 | Bearer JWT | `?pod=xx&container=xx&tail=100` |
| `GET /stream/deploy/:deploy_id/progress` | 部署进度 | Bearer JWT | — |
| `GET /stream/notifications` | 全局通知（集群状态、告警） | Bearer JWT | — |

认证走标准 HTTP `Authorization: Bearer <jwt>`，和 REST API 完全一致。

### 6.2 SSE 消息格式

标准 SSE 格式：`event:` + `data:` + `id:`（用于断点续传）

**实例状态流** `GET /stream/instances/:id/status`

```
event: instance_status
id: evt-1707554321-001
data: {"instance_id":"xxx","status":"running","replicas":1,"available":1,"pods":[{"name":"...","status":"Running","restart_count":0}]}

event: pod_changed
id: evt-1707554322-002
data: {"pod":"xxx-m4p8q","status":"Running","phase":"Running","restart_count":0}
```

**K8s 事件流** `GET /stream/instances/:id/events`

```
event: k8s_event
id: evt-1707554345-003
```

### 6.3 前端使用

```typescript
// 浏览器 EventSource — 内置自动重连 + Last-Event-ID 断点续传
const es = new EventSource('/api/v1/stream/instances/xxx/logs?pod=xx&container=openclaw&tail=100', {
  headers: { 'Authorization': `Bearer ${token}` }  // 需要 polyfill 或 fetch-based SSE
});
es.addEventListener('log', (e) => appendLog(JSON.parse(e.data)));
es.addEventListener('log_end', () => es.close());

// 关闭页面 → 连接自动断开 → 后端 generator 清理
```

> 注意：原生 `EventSource` 不支持自定义 Header。实例级 SSE 流用 `@microsoft/fetch-event-source` 或类似库支持 Bearer Token。工作区 events 端点改用原生 `EventSource` + URL query parameter 传递短时效 SSE token（`POST /workspaces/sse-token` 签发，5 分钟有效）。

### 6.4 后端实现要点

- 用 FastAPI `StreamingResponse(generator(), media_type="text/event-stream")`
- 实例级 SSE 流走标准 `Depends(get_current_user)` 认证（Authorization 请求头）
- 工作区 events 端点走 `Depends(get_current_user_from_query)` 从 URL `?token=` 读 JWT（因 `EventSource` 不支持自定义请求头）
- 每个 SSE 连接对应一个 `async generator`，内部调 K8s Watch/日志流
- 客户端断开 → generator 被 cancel → 自动清理 K8s Watch
- 心跳：每 30 秒发 `:keepalive\n\n`（SSE 注释行），防止代理超时
- HTTP/2 下多个 SSE 连接复用同一 TCP，不浪费

### 7.4 RBAC 权限模型

#### 双表职责分离

管理平台和 Portal 的角色由两张独立的表管理，互不干扰：

| 表 | 用途 | 谁写 | 谁读 |
|----|------|------|------|
| `org_memberships` | Portal 组织角色（admin/member） | OAuth 登录自动创建 | Portal |
| `admin_memberships` | 管理平台角色（member/operator/admin） | 管理员手动创建 | Admin |

**有 AdminMembership 记录 = 有管理平台权限，无记录 = 无权限。**

#### 管理平台角色层级（admin_memberships.role）

| 角色 | 层级值 | 含义 |
|------|--------|------|
| member | 10 | 只读：Dashboard、实例列表/详情/日志/监控/事件 |
| operator | 20 | 运维操作：部署、重启、扩缩容、配置变更 |
| admin | 30 | 完全权限：集群管理、系统设置、基因运营、成员管理 |

`is_super_admin` 保持不变，绕过所有管理平台权限检查。

新用户 OAuth 登录后仅创建 `OrgMembership`（Portal 组织成员），不创建 `AdminMembership`。需管理员在成员管理页面手动添加后才能访问管理平台。

#### 管理平台成员 API（/api/v1/admin/members）

| 方法 | 路径 | 说明 | 最低角色 |
|------|------|------|---------|
| GET | /admin/members | 列出管理平台成员 | admin |
| POST | /admin/members | 添加管理平台成员 | admin |
| PUT | /admin/members/{id} | 修改成员角色 | admin |
| DELETE | /admin/members/{id} | 移除管理平台权限（软删除） | admin |

#### Portal / Admin 路由架构

Portal 和 Admin 使用**完全独立的路由文件**，不共享 router 对象。两套路由共用底层 service 层。

- `/api/v1/...` — Portal 使用，路由定义在 `app/api/portal/` 目录，内置实例级权限检查
- `/api/v1/admin/...` — 管理平台使用，路由定义在 `app/api/` 目录（instances.py、deploy.py 等），通过 `require_org_role(min_role)` 检查 `admin_memberships` 表

Portal 独立路由文件：

| 文件 | 职责 |

| `app/api/portal/instances.py` | 实例 CRUD（内置 InstanceMember 权限检查） |

### 8.3 K8s API 错误处理

```python
async def safe_k8s_call(func, *args, **kwargs):
    """包装 K8s API 调用，统一处理异常"""
    try:
        return await func(*args, **kwargs)
    except ApiException as e:
        if e.status == 401:
            raise ClusterError(20003, "集群认证失败，请检查 KubeConfig")
        elif e.status == 403:
            raise ClusterError(20004, "权限不足，请检查 RBAC 配置")
        elif e.status == 404:
            raise InstanceError(30002, "资源不存在")
        else:
            raise ClusterError(20099, f"K8s API 错误: {e.reason}")
    except MaxRetryError:
        raise ClusterError(20001, "集群连接失败，请检查网络")
```

## 十二、多集群网关流量路由

NoDeskClaw 采用 infra + inst 双集群架构：

- **infra 集群**：运行管理平台（后端 API、admin 前端、portal 前端、LLM Proxy）
- **inst 集群**：运行 OpenClaw 实例，支持多个 inst 集群

### 流量链路

```
用户浏览器
  → DNS: *.nodeskai.com → infra ALB（TLS 终止）
    → infra nginx-ingress-controller
      → 管理平台子域名（admin-claw/console-claw 等）→ 本地 Service
      → 实例子域名（{slug}-claw）→ ExternalName Service → inst 集群 ALB
        → inst nginx-ingress-controller
          → 实例 Ingress → ClusterIP Service → OpenClaw Pod
```

### 关键机制

- **ExternalName Service**：每个 inst 集群在 infra 的 `nodeskclaw-system` 命名空间有一个 ExternalName Service（`proxy-inst-{cluster_id}`），指向该集群的 ALB hostname
- **Proxy Ingress**：每个实例在 infra 上有一条 proxy Ingress（`proxy-{instance_name}`），将子域名流量转发到对应 inst 集群的 ExternalName Service
- **Gateway Client**：后端 Pod 通过 in-cluster config 操作 infra 集群 API（无需存储 infra kubeconfig），通过 DB 存储的 kubeconfig 操作 inst 集群
- **Cluster.proxy_endpoint**：inst 集群的 ALB hostname，不为空时自动创建代理资源
- **RBAC**：后端 ServiceAccount 通过 `nodeskclaw-gateway-proxy` Role 获得在 `nodeskclaw-system` 命名空间管理 Ingress/Service 的权限

### 部署流水线双集群写入

Step 7（Ingress 创建）扩展为：
1. 在 inst 集群创建实例 Ingress（原逻辑不变）
2. 通过 gateway client 在 infra 集群创建 proxy Ingress + ExternalName Service

实例删除时同步清理 infra 上的 proxy Ingress。

## 十三、持久化存储架构

### 13.1 架构决策

OpenClaw 实例需要持久化存储来保存运行数据（配置、聊天记录等），挂载到容器的 `/root` 目录。

**决策**: 使用火山云 NAS 极速型 + NFS CSI 动态供给（subpath 模式）。

**原因**:
- 火山云 EBS 云盘仅支持 `ReadWriteOnce`，不适合多副本或迁移场景
- NAS NFS 支持 `ReadWriteMany`，一块 NAS 可通过 subpath 模式被多个 PVC 共享
- 动态供给每个 PVC 自动创建子目录，无需手动创建 PV
- `archiveOnDelete: true` 在 PVC 删除时仅归档子目录（重命名），不物理删除数据
- `reclaimPolicy: Delete` 自动回收 PV，避免 Released PV 累积（`archiveOnDelete` 已保障数据安全）

### 13.2 StorageClass 管理

- 集群管理员需要手动 `kubectl apply` 创建 StorageClass（一次性操作）
- YAML 模板: `nodeskclaw-artifacts/k8s/nas-storageclass.yaml`
- 前提: VKE 集群需安装 `csi-nas` 组件
- 未来添加新存储类型（如容量型 NAS）也是同样流程：创建新的 StorageClass

### 13.3 实例级存储选择

每个实例独立记录使用的 StorageClass（`instances.storage_class` 字段），部署时用户可在前端选择：

```
GET /api/v1/storage-classes
→ 从 K8s 集群动态读取可用 StorageClass 列表
→ 前端部署页在「资源配额」步骤展示下拉选择器
→ 选择结果随 DeployRequest 一起提交到后端
→ 后端 deploy_service.py 使用该值创建 PVC
```

### 13.4 PVC 访问模式

所有 PVC 统一使用 `ReadWriteMany` 访问模式（NFS 天然支持）。

### 13.5 PV 生命周期管理

实例删除/部署失败时，`delete_namespace()` 会级联删除 PVC。`reclaimPolicy: Delete` 使 PV 自动回收。

作为兜底，`instance_service` 和 `deploy_service` 在删除 Namespace 后会启动后台任务，延迟 15 秒轮询并清理残留的 Released PV（`K8sClient.cleanup_released_pvs`），最多重试 3 次。

### 13.6 未来迁移方案

数据模型已支持实例级存储切换，未来实现跨存储迁移时：

1. 创建新 PVC（目标 StorageClass）
2. 启动 Job 将旧 PVC 数据拷贝到新 PVC
3. 更新 Instance 的 `storage_class` 和 Deployment 的 volume 引用
4. 删除旧 PVC

## 十五、工作区群聊协同

### 核心概念

工作区 = 群聊室。用户消息广播给所有 Agent，各 Agent 根据自身设定决定是否回复。每个 Agent 是独立的 OpenClaw 实例，session 存储物理隔离，NoDeskClaw 负责消息同步。

### 通信架构（SSE 长连接）

原先的 HTTP Webhook 方式（`POST /webhook/nodeskclaw`）已废弃，改为 **SSE 长连接**：

- **Channel Plugin** 在实例内启动 SSE 服务（端口 9721，Node.js 内置 `http` 模块，零依赖）
- **后端** 主动连接各实例的 SSE 端点：`https://<ingress_domain>/sse/events`
- **心跳**：Plugin 每 15 秒发送 heartbeat，后端 45 秒内无事件则视为连接死亡
- **无监听检测**：Plugin 的 `sendText()` 在 `clients.size === 0` 时抛错，提示无后端连接

### 连接生命周期

| 时机 | 动作 |
|------|------|
| Agent 加入工作区（含重启后） | 后端建立到该实例的 SSE 连接 |
| Agent 离开工作区 | 后端断开对应 SSE 连接 |
| 后端启动 | 恢复所有运行中实例的 SSE 连接 |

### 数据模型

```python
class WorkspaceMessage(BaseModel):
    workspace_id: str       # FK -> workspaces.id
    sender_type: str        # "user" | "agent" | "system"
    sender_id: str          # user_id / instance_id / "system"
    sender_name: str
    content: str
    message_type: str       # "chat" | "collaboration" | "system"
    target_instance_id: str | None
    depth: int              # 防循环深度计数

class WorkspaceChatRequest(BaseModel):
    message: str
    mentions: list[str] | None = None   # @ 提及的 Agent instance_id 列表
```

### API 端点

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/workspaces/{ws}/chat` | 群聊广播：用户消息发给所有 Agent。请求体 `{ message, mentions? }` |
| GET | `/workspaces/{ws}/messages` | 获取工作区消息历史 |
| POST | `/workspaces/{ws}/system-message` | 持久化系统消息（斜杠命令结果等），不触发 Agent 回复 |
| GET | `/workspaces/{ws}/events?token=xxx` | SSE 事件流（含 agent:typing/chunk/done/error/collaboration/status、system:welcome/info） |
| POST | `/workspaces/sse-token` | 签发 5 分钟短时效 SSE token |

**events 端点认证**：浏览器 `EventSource` 不支持自定义 HTTP 请求头，因此 events 端点通过 URL query parameter `?token=` 传递 JWT。前端先调 `POST /workspaces/sse-token` 获取短时效 token，降级时使用 access token。后端通过 `get_current_user_from_query` 依赖从 query 读取并验证。

> 不再提供 `POST /webhook/nodeskclaw`。Agent 消息通过 SSE 长连接由后端主动拉取。

### 消息流

1. 用户发送消息 -> 记录到 `workspace_messages` -> 查询运行中 Agent
2. **拓扑过滤**：若工作区有 corridor 连接（`has_any_connections`），仅向从黑板 (0,0) 可达的 Agent 广播。无连接时向所有运行中 Agent 广播
3. 如请求携带 `mentions`（@ 提及 instance_id 列表），被 @ 的 Agent system prompt 追加"必须回复"提示；未被 @ 的 Agent 追加"可 NO_REPLY"提示。无 mentions 时保持原有全广播行为
4. 每个 Agent 通过独立 `asyncio.Task` 流式响应（task 引用存入 `_background_tasks` 集合防止 GC 回收）
5. 前 20 字符缓冲检测 `NO_REPLY`（OpenClaw 内置静默标记）-> 丢弃内容，但仍广播 `agent:done`（不含 `full_content`）以清除前端 typing 指示器
6. 若没有运行中 Agent 或拓扑过滤后无可达 Agent，通过 `system:info` SSE 事件通知前端（完整字段：id、sender_type、sender_id、sender_name、content、message_type、created_at）
7. Agent 主动协同：`send -t nodeskclaw -to "agent:xxx"` -> Plugin 通过 SSE 广播 -> 后端 `sse_listener` 接收 -> `collaboration_service` 路由到目标 Agent

### Agent 加入工作区

1. 设置 hex 位置（用户指定或自动 spiral 分配）
2. **自动连接**：调用 `corridor_router.auto_connect_hex()` 创建到所有相邻已占 hex 的双向连接
3. **拓扑通知**：若工作区有拓扑，通过 `system:info` SSE 事件通知前端连接状态（已连接的邻居列表，或无邻居时的孤岛警告）
4. 部署 Channel Plugin、发送欢迎消息

### Agent 状态实时推送

实例状态变化（如重启完成 `restarting -> running`）由 `_monitor_restart` 异步任务监控，完成后通过 `agent:status` SSE 事件广播到工作区前端，前端实时更新 agent 列表中的状态徽标，无需手动刷新。

基因学习期间实例状态为 `learning`，通过 `agent:status` SSE 事件广播到工作区。当一个实例同时学习多个基因时（如应用基因组批量安装），实例保持 `learning` 状态直到所有基因学习完成（成功或失败），之后才执行 restart 恢复为 `running`。辅助函数 `_has_pending_learning(db, instance_id, exclude_ig_id)` 用于检查是否还有其他基因处于学习中。

### SSE 连接健康状态

`SSEListenerManager` 通过 `_healthy` 集合精确跟踪每个实例的实际 SSE 连接状态（区别于 `connected_instances` 仅表示 task 未结束）：

- **连接成功**（`_listen_once` 收到 200 响应）-> `_healthy.add(instance_id)` + 广播 `agent:sse_connected` 事件
- **连接断开**（异常/超时/取消）-> `_healthy.discard(instance_id)` + 广播 `agent:sse_disconnected` 事件
- **实例删除** -> `delete_instance()` 中主动调用 `sse_listener_manager.disconnect()` 断开连接，避免幽灵连接无限重试

**启动恢复**：lifespan 中查询 `status IN ('running', 'restarting', 'learning')` 的工作区实例，对卡在 `restarting` 或 `learning` 的实例自动恢复为 `running`（防止后端重启导致异步任务丢失而状态卡死），然后为所有实例建立 SSE 连接。

`AgentBrief` schema 包含 `sse_connected: bool`、`theme_color: str | None` 和 `label: str | None` 字段。`sse_connected` 由 `_agent_brief()` 查询 `sse_listener_manager.healthy_instances` 填充。`theme_color` 来自 `Instance.agent_theme_color`（VARCHAR(7), CSS hex 格式如 `#4ade80`），支持用户在工作区画布中为每个 Agent 单独设置机器人主题色。`label` 来自 `Instance.agent_label`（VARCHAR(128)），用于在工作区画布中显示 Agent 的职责描述标签，与显示名称一起展示在六边形上。前端工作区画布根据这些字段展示连接状态视觉差异、自定义配色和名称标签。

### 系统消息持久化

斜杠命令（`/status`、`/restart`、`/remove` 等）的结果通过 `POST /workspaces/{ws}/system-message` 持久化到 `workspace_messages` 表（`sender_type="system"`），并通过 `system:info` SSE 事件广播。刷新页面后仍可在聊天历史中看到。`/clear` 例外，仅清空前端显示。

### Agent 入群欢迎消息

Agent 加入工作区后分两步处理：

**即时加入通知**（`_broadcast_join_message`，同步执行）：

1. `add_agent()` 完成 channel plugin 部署后，立即记录 `sender_type="system"` 消息到 DB
2. 广播 `system:welcome` SSE 事件到前端，前端以居中灰色气泡展示（如"AgentXXX 已加入工作区"）

**异步自我介绍**（`_send_welcome_message`，后台任务）：

1. 检查 SSE listener 是否在运行（判断实例是否被重启）
2. 若 SSE listener 在运行（正常路径）：轮询 `sse_listener_manager.healthy_instances`（每 3 秒，最长 120 秒），等待实例就绪后再发送。SSE connected 后额外缓冲 3 秒
3. 若 SSE listener 未运行（channel 部署失败降级路径）：短延迟 10 秒后尝试（实例未被重启，仍在运行）
4. 调用 `collaboration_service._invoke_target_agent()` 向 Agent 发送自我介绍提示
5. Agent 的回复通过 `agent:typing` -> `agent:chunk` -> `agent:done` 事件链自动出现在群聊中
6. `_invoke_target_agent` 返回 `bool` 标识成功/失败，非 200 响应会记录 error 日志

### Agent 退出工作区通知

Agent 被移出工作区时，`remove_agent()` 在清除数据之前调用 `_broadcast_leave_message`：

1. 记录 `sender_type="system"` 消息到 DB（内容为"AgentXXX 已退出工作区"），确保刷新后仍可见
2. 广播 `system:info` SSE 事件到前端，复用已有的系统消息渲染逻辑（居中灰色气泡）
3. 必须在清除 `agent_display_name` 之前执行，否则无法获取显示名称

### Session 机制

- Header: `X-OpenClaw-Session-Key: workspace:{workspace_id}`
- 上下文注入通过 `system` role（成为 `extraSystemPrompt`，不存入 session）
- 只注入**其他成员**的近期消息，避免与 Agent 自身 session 重复

### Channel Plugin

独立包 `openclaw-channel-nodeskclaw`，零运行时依赖，通过 NFS 分发 `.ts` 源文件到各实例，jiti 直接加载。

- **SSE 服务**：`src/sse-server.ts`，在 `index.ts` 注册时启动，监听 9721
- **广播**：`src/channel.ts` 的 `sendText()` 向所有已连接的后端客户端推送事件
- **原生工具**：`src/tools.ts` 定义 5 个 Agent 工具（blackboard/topology/performance/proposals/gene_discovery），在 `index.ts` 中以 `optional: true` 注册，通过 `tools.allow` 激活

### Learning Channel Plugin

独立插件 `openclaw-channel-learning`，与 nodeskclaw plugin 同构部署。支持学习模式和创造模式两种任务。

### 学习引擎

1. 用户请求学习基因
2. 后端去重检查 + 创建 InstanceGene
3. 检查 Agent 是否有 meta-learning 基因
4. 有学习能力：
   - 检测 SKILL.md 内容是否包含 YAML frontmatter（`_has_frontmatter()`）
   - **缺少 frontmatter**：`force_deep_learn=True`，强制深度学习。Agent 不能选择 `direct_install`，必须输出包含完整 YAML frontmatter（`name`、`description`、`metadata.openclaw` 等）的 SKILL.md。后端通过 `config_snapshot` 记录 `force_deep_learn` 状态，回调时如果 Agent 仍选择 `direct_install` 则 fallback 到自动补全 frontmatter 安装
   - **有 frontmatter**：Agent 自主决定 `direct_install`（直接安装）或 `learned`（深度学习后生成个性化版本）
5. 无学习能力：status=installing -> 直接写入 SKILL.md（自动补 `name` + `description` frontmatter）
6. 合并 openclaw.json + 重启
7. SSE 通知前端

### 实例级串行安装（PostgreSQL Advisory Lock）

`apply_genome` 会循环调用 `install_gene`，每次通过 `_fire_task(asyncio.create_task(...))` 将 `_direct_install` 发射为后台任务。多个任务并发执行时共享同一个 NFS 挂载点，先完成的任务 `umount` 后，未完成的任务写入失败。

**解决方案**：在 `_direct_install` 和 `_direct_uninstall` 入口使用 PostgreSQL session 级 Advisory Lock（`pg_advisory_lock` / `pg_advisory_unlock`），以 `hash(instance_id) % 2^31` 为 lock key，确保同一实例的 NFS 操作串行执行。

```
_fire_task(_direct_install(inst_A, gene_1))   ─┐
_fire_task(_direct_install(inst_A, gene_2))    │ PG Advisory Lock 排队
_fire_task(_direct_install(inst_A, gene_3))    │ gene_1 完成 → gene_2 开始 → gene_3 开始
                                               ─┘
_fire_task(_direct_install(inst_B, gene_4))   ─── 不同实例，不同 lock key，不受影响
```

| 特性 | 说明 |
|------|------|
| 锁粒度 | 实例级，不同实例互不阻塞 |
| 分布式支持 | PG 锁天然跨进程/跨后端副本生效 |
| `_fire_task` 不变 | API 立即返回，前端体验无影响 |
| 专用连接 | 锁使用独立 DB session，不影响业务事务 |
| `_send_learning_task` / `_send_forgetting_task` | 不加锁，其 NFS 操作通过 fallback 调用 `_direct_install` / `_direct_uninstall` 时由被调函数自行加锁 |

### 基因工程化能力

基因不仅包含语义能力（SKILL.md，Agent 学习），还可携带工程化能力（直接修改平台配置，无需学习）。

#### manifest 结构

```json
{
  "skill": { "slug": "xxx", "name": "xxx", "content": "..." },
  "openclaw_config": { "任意 openclaw.json 字段": "值" },
  "tool_allow": ["nodeskclaw_blackboard", "nodeskclaw_topology"],
  "learning": { "force_deep_learn": false }
}
```

- `skill`：语义能力，写入 SKILL.md 供 Agent 学习
- `openclaw_config`：浅合并到 `openclaw.json`（覆盖同名顶层字段）
- `tool_allow`：追加到 `openclaw.json` 的 `tools.allow` 数组（去重）
- `learning`：学习策略控制

#### 统一执行函数 `_apply_engineering_actions`

`gene_service.py` 中的 `_apply_engineering_actions(mount_path, manifest)` 在基因安装的所有路径（直接安装、深度学习回调 direct_install 分支、深度学习回调 learned 分支）统一执行工程化能力：

1. 读取 manifest 中的 `openclaw_config` 字段，调用 `_merge_openclaw_config()` 浅合并到 `openclaw.json`
2. 读取 manifest 中的 `tool_allow` 字段，调用 `_append_tool_allow()` 去重追加到 `tools.allow` 数组

#### `_append_tool_allow` 去重逻辑

`_append_tool_allow(mount_path, tool_names)` 读取 `openclaw.json`，取出 `tools.allow` 数组，将新 tool name 逐个检查后追加（已存在则跳过），写回文件。避免多个基因安装同一工具时产生重复。

### 深度遗忘流程

`uninstall_gene()` 根据 Agent 是否具备 meta-learning 能力分支处理：

| 分支 | 条件 | 行为 |
|------|------|------|
| 深度遗忘 | 有 meta-learning 基因 | Agent 参与遗忘决策，通过 Learning Channel Plugin 执行 |
| 直接卸载 | 无 meta-learning 基因 | 直接删除 SKILL.md、更新 openclaw.json、重启实例 |

**深度遗忘流程**：

1. `_send_forgetting_task()`：向 Learning Channel Plugin 发送 webhook，触发 Agent 遗忘任务
2. Plugin 内 Agent 执行遗忘逻辑，完成后回调 `handle_forgetting_callback()`
3. `handle_forgetting_callback()` 处理三种结果：
   - **forgotten**：完全移除，删除 InstanceGene 记录，清除 skill 文件
   - **simplified**：技能降级保留，更新 InstanceGene 为 `status=simplified`，写入简化版 SKILL.md
   - **forget_failed**：遗忘失败，回滚到原状态

**进化事件记录**：在以下时机写入 `EvolutionEvent` 表：

- 学习完成 / 学习失败
- 遗忘完成 / 遗忘失败 / 简化完成
- 发布变体
- 应用基因组

综合效能分 = 用户评分 25% + Agent 自评 25% + 使用效能 50%

### 人类工位消息投递

当 Agent 的协作消息路由到 Human Hex 时，`collaboration_service._deliver_to_human()` 按以下优先级投递：

1. **群聊投递** — Human Hex 的 `channel_config.chat_id` 存在 → `receive_id_type: "chat_id"`
2. **私聊投递** — 查 `user_oauth_connections` 拿用户的飞书 `open_id` → `receive_id_type: "open_id"`
3. **SSE 回退** — 以上都不可用 → 仅推 workspace SSE `human:message_delivered` 事件

投递使用 `FeishuChannelAdapter.send_card()` 发送交互式卡片，卡片含工作区名、来源 Agent、消息内容（截断 500 字）。

**回复路由**：飞书回复通过 webhook / WebSocket 两条路径进入后端，`_handle_message_event` 统一处理：

1. 先按 `chat_id` 匹配 `HumanHex.channel_config`（群聊场景）
2. 无匹配则按 `sender.open_id` → `user_oauth_connections.provider_user_id` → `HumanHex.user_id` 匹配（私聊场景）
3. 私聊场景若用户在多个工作区有 Human Hex，取最近创建的
4. 匹配到的 Human Hex 经 BFS 路由找到可达 Agent，调用 `send_system_message_to_agents` 投递

## MCP 集成

### 原生工具架构

NoDeskClaw 的 MCP 能力通过 OpenClaw 的 `registerTool` API 以原生 Agent 工具形式提供，而非外挂 MCP Server 进程。

**工具注册**：`openclaw-channel-nodeskclaw/src/tools.ts` 定义 5 个原生工具，在 `index.ts` 的 `register` 函数中通过 `api.registerTool(tool, { optional: true })` 注册。`optional: true` 意味着工具注册后默认不启用，需在 `openclaw.json` 的 `tools.allow` 数组中列出工具名才会对 Agent 可用。

**基因驱动激活**：每个工具对应一个基因，基因 manifest 中的 `tool_allow` 字段指定要激活的工具名，`skill` 字段包含 SKILL.md 教 Agent 如何使用工具。安装基因时 `_apply_engineering_actions` 自动将工具名追加到 `tools.allow`（去重）并写入 SKILL.md。

| 工具名 | 对应基因 slug | 功能 |
|--------|----------|------|
| `nodeskclaw_blackboard` | `mcp_blackboard_tools` | 读写工作区黑板（任务、目标） |
| `nodeskclaw_topology` | `mcp_topology_awareness` | 查询拓扑图、成员、邻居 |
| `nodeskclaw_performance` | `mcp_performance_reader` | 读取绩效指标 |
| `nodeskclaw_proposals` | `mcp_proposals` | 提交审批申请、检查信任策略 |
| `nodeskclaw_gene_discovery` | `mcp_gene_discovery` | 搜索基因市场、请求学习基因 |

### 基因组

| 基因组 slug | 包含基因 | 说明 |
|-------------|----------|------|
| `nodeskclaw_workspace_toolkit` | 上述全部 5 个基因 | 一键安装全部工作区协作工具，推荐作为新 Agent 默认基因组 |

### 种子数据

5 个基因和 1 个基因组的 SQL 种子数据位于 `scripts/seed_mcp_genes.sql`，使用 `ON CONFLICT (slug) WHERE deleted_at IS NULL DO NOTHING` 保证幂等，可重复执行。

## 企业空间文件浏览

### 概述

企业空间允许组织管理员通过 Portal 以只读方式浏览所有 Agent 实例内的文件，解决文件散落在不同 Agent 之间难以管理的问题。

### 技术方案

复用现有 PodFS 机制（`nfs_mount.py`），通过 `kubectl exec` 实时读取运行中实例 Pod 的文件系统。

- 后端（基础设施集群）与实例（实例集群）在不同 K8s 集群，无法直接挂载 NAS
- PodFS 跨集群 exec 已在生产稳定运行，被 `gene_service`、`llm_config_service`、`channel_config_service`、`openclaw_session` 等服务使用
- 零基础设施变更：不新增 NFS 卷挂载、不新增数据库表

### PodFS 扩展

`PodFS` 类新增 `list_dir` 方法，单次 exec 调用 `find -printf` 获取目录内容及元数据（文件名、类型、大小、修改时间）。

### 权限控制

- 使用 `OrgMembership` 做组织级权限检查（`require_org_admin` 依赖）
- MVP 仅对组织 admin 开放
- 注意：`require_org_role` 是 Admin 路由专用（检查 AdminMembership），Portal 路由使用 `require_org_admin`

### 安全策略

| 策略 | 说明 |
|------|------|
| 路径穿越防护 | 禁止 `..` 路径组件 |
| 敏感路径黑名单 | `credentials/`、`.env`、`node_modules/`、`temp/` |
| 文件大小限制 | 预览上限 1MB |
| 浏览根限制 | 所有路径限制在 `.openclaw/` 下 |

### 企业空间 API（Portal /api/v1/enterprise-files）

| 方法 | 路径 | 说明 | 权限 |
|------|------|------|------|
| GET | /agents | 列出组织下所有 Agent 及可浏览状态 | org admin |
| GET | /agents/{instance_id}/files | 列出指定目录的文件（query: path） | org admin |
| GET | /agents/{instance_id}/files/content | 读取文件内容（仅文本） | org admin |
| GET | /agents/{instance_id}/files/download | 下载文件原始内容 | org admin |

### 实例级文件管理 API（Portal /api/v1/instances/{instance_id}/files）

在实例详情页提供文件读写能力，仅实例 admin 可访问。权限通过 `instance_member_service.check_instance_access(instance_id, user, InstanceRole.admin, db)` 检查。
