# 双前端方案 — 用户门户（User Portal）设计

> 状态：RFC（征求意见）  
> 日期：2026-02-16  
> 作者：NoDeskClaw Team

## 1. 背景与动机

### 1.1 问题

当前 NoDeskClaw 管理面板（Admin Panel）面向运维和开发人员设计，界面中充斥大量 K8s 专业术语：

- Namespace、Pod、Deployment、Service、Ingress
- CPU Request/Limit、Memory Request/Limit
- StorageClass、PVC、ConfigMap
- YAML 预览、滚动更新、扩缩容

对于**没有技术背景的普通用户**（产品、设计、运营等），这些概念构成了极高的使用门槛。他们的核心诉求只是：

> "我想要一个自己的 AI 编程助手，能用就行。"

### 1.2 参考

- **VibeCraft**：将多 AI Agent 管理简化为"RTS 游戏式"可视化界面，用户只需点击分配任务
- **Vercel / Railway**：一键部署，技术细节全部隐藏
- **Notion AI**：零配置开箱即用

核心启示：**对普通用户做减法，而不是加注释**。

### 1.3 方案选型

| 方案 | 优点 | 缺点 |
|------|------|------|
| **A. 双前端**（独立 User Portal） | 两类用户体验独立优化，互不干扰 | 多一个前端项目需维护 |
| B. 单前端 + 角色切换 | 一套代码 | 两种需求硬塞一起，UX 妥协多 |
| C. Admin 面板加"简洁模式"开关 | 改动最少 | 简化有限，技术味去不掉 |

**结论：采用方案 A — 双前端。**

理由：
- 两类用户的核心需求完全不同（管理 vs 使用）
- User Portal 可以做得极轻（5-8 个页面）
- 后端 API 100% 复用，零改动
- 未来可独立部署、独立迭代

## 3. User Portal 功能范围

### 3.1 包含（用户需要的）

| 页面 | 功能 | 说明 |
|------|------|------|
| **登录** | 飞书 SSO | 复用现有 OAuth 流程 |
| **首页（我的实例）** | 实例卡片列表 | 只显示当前用户创建的实例 |
| **一键创建** | 极简创建流程 | 见 §4 详细设计 |
| **实例详情** | 运行状态 + 直达链接 | 简化版，不暴露 Pod/K8s 细节 |
| **实例设置** | API Key 管理 | 配置 OpenAI/Anthropic 等大模型 Key |
| **创建进度** | 部署等待页 | 友好的进度动画，隐藏技术日志 |

### 3.2 排除（管理员专属）

以下功能**只在 Admin Panel 提供**，User Portal 中不出现：

- 集群管理（添加/编辑/删除集群）
- 系统设置（镜像仓库、域名配置）
- 资源配额精细调整（CPU/内存/存储）
- YAML 预览
- Pod 列表 / 容器详情
- K8s 事件流
- 高级配置（Sidecar、Init Container、Volume）
- 全局部署历史

### 3.3 灰色地带（按需开放）

| 功能 | 建议 |
|------|------|
| 实例日志 | 提供简化版"查看日志"按钮，只显示最近 N 条 |
| 扩缩容 | 不开放，使用固定 1 副本 |
| 滚动更新 | 不开放，由管理员统一升级镜像版本 |
| 实例删除 | 开放，需二次确认 |
| 部署历史 | 简化为"最近一次部署状态" |

## 4. 核心交互设计

### 4.1 一键创建流程

与 Admin Panel 的 4 步向导对比：

```
Admin Panel（现有）：              User Portal（新增）：
┌──────────────────┐             ┌──────────────────┐
│ 1. 基本信息       │             │                  │
│    名称           │             │  给你的 AI 助手   │
│    镜像版本       │     →       │  起个名字:        │
│    副本数         │             │  [           ]   │
├──────────────────┤             │                  │
│ 2. 资源配额       │             │  选个规格:        │
│    CPU Req/Limit │             │  ○ 轻量  ● 标准  │
│    Mem Req/Limit │             │  ○ 高性能         │
│    StorageClass  │             │                  │
├──────────────────┤             │  [创建我的助手]    │
│ 3. 环境变量       │             │                  │
│    KEY=VALUE     │             └──────────────────┘
├──────────────────┤
│ 4. 确认部署       │
│    预检          │
│    YAML 预览     │
│    高级配置       │
└──────────────────┘
```

**关键简化：**
- 镜像版本：自动使用最新稳定版，用户不需要知道
- 副本数：固定 1
- 资源配额：三档选择（轻量/标准/高性能），无技术参数外露
- 环境变量：不在创建时要求，创建后在"设置"里配 API Key
- 预检/YAML：自动完成，用户看不到
- Namespace：自动生成，用户无感知

### 4.2 实例卡片

```
┌─────────────────────────────────────┐
│  🟢 我的编程助手                      │
│                                     │
│  状态: 运行中                        │
│  创建于: 2 天前                      │
│  规格: 标准                          │
│                                     │
│  [打开控制台 →]     [⚙ 设置]         │
└─────────────────────────────────────┘
```

不显示：Namespace、Pod IP、Image Version、CPU/Mem、Ingress Domain 等。

### 4.3 实例设置页

```
┌─────────────────────────────────────┐
│  ⚙ 我的编程助手 - 设置               │
│                                     │
│  大模型配置                          │
│  ┌─────────────────────────────┐   │
│  │ 提供商:  [OpenAI    ▾]     │   │
│  │ API Key: [sk-**********]   │   │
│  │          [保存]             │   │
│  └─────────────────────────────┘   │
│                                     │
│  实例信息                            │
│  名称: 我的编程助手                   │
│  规格: 标准 (4c / 8Gi)              │
│  访问地址: https://xxx.nodeskai.com  │
│                                     │
│  危险操作                            │
│  [删除此实例]                        │
└─────────────────────────────────────┘
```

**API Key 配置的技术实现：**
- 前端提供下拉选择大模型提供商（OpenAI / Anthropic / Google / OpenRouter）
- 提交后后端将对应的环境变量（如 `OPENAI_API_KEY`）注入到实例的 ConfigMap
- 触发 Pod 滚动重启使其生效

## 5. 技术方案

### 5.1 项目结构

```
NoDeskClaw/
├── nodeskclaw-frontend/        # Admin Panel（现有，不动）
├── nodeskclaw-portal/          # User Portal（新增）
│   ├── src/
│   │   ├── views/
│   │   │   ├── Login.vue           # 飞书登录
│   │   │   ├── Home.vue            # 我的实例列表
│   │   │   ├── Create.vue          # 一键创建
│   │   │   ├── Progress.vue        # 创建进度
│   │   │   ├── Instance.vue        # 实例详情
│   │   │   └── Settings.vue        # 实例设置（API Key）
│   │   ├── components/
│   │   ├── stores/                 # Pinia stores（可部分复用）
│   │   ├── services/               # API 层（复用 api.ts 配置）
│   │   └── router/
│   ├── package.json
│   └── vite.config.ts
├── nodeskclaw-backend/          # 后端（完全复用，不改）
└── ...
```

### 5.2 技术栈

与 Admin Panel 保持一致，降低维护成本：

| 类别 | 选型 |
|------|------|
| 框架 | Vue 3 + TypeScript |
| UI | shadcn-vue + Tailwind CSS |
| 构建 | Vite |
| 状态 | Pinia |
| 路由 | Vue Router |
| 图标 | lucide-vue-next |
| 通知 | 自定义 Notify 组件（复用） |

### 5.3 后端复用

User Portal 调用的全部是现有 API，不需要新增后端接口：

| 功能 | 现有 API |
|------|---------|
| 登录 | `POST /api/v1/auth/feishu/callback` |
| 实例列表 | `GET /api/v1/instances?cluster_id=` |
| 创建实例 | `POST /api/v1/deploy` |
| 部署进度 | `GET /api/v1/deploy/{id}/progress`（SSE） |
| 实例详情 | `GET /api/v1/instances/{id}` |
| 修改配置 | `PUT /api/v1/instances/{id}/config` + `POST /apply` |
| 删除实例 | `DELETE /api/v1/instances/{id}` |
| 镜像版本 | `GET /api/v1/registry/tags` |
| 获取设置 | `GET /api/v1/settings` |

唯一可能需要的后端调整：
- 实例列表增加 `created_by` 过滤（让用户只看到自己的实例）
- 预检接口自动跳过用户不需要关心的检查项

### 5.4 部署

| 环境 | Admin Panel | User Portal |
|------|------------|-------------|
| 开发 | localhost:5173 | localhost:5174 |
| 生产 | admin.nodeskclaw.nodeskai.com | portal.nodeskclaw.nodeskai.com |

两个前端打出的静态文件可以部署在同一个 Nginx / CDN 下，通过子域名路由。

## 6. 规格档位映射

User Portal 中对用户展示的"规格"与 Admin Panel 中实际资源配置的映射：

| 用户看到的 | 内部名称 | Namespace 配额 | CPU Req/Limit | 内存 Req/Limit | 存储 |
|-----------|---------|---------------|--------------|---------------|------|
| 轻量 | small | 2c / 4Gi | 1000m / 2000m | 2Gi / 4Gi | 40Gi |
| 标准 | medium | 4c / 8Gi | 2000m / 4000m | 4Gi / 8Gi | 80Gi |
| 高性能 | large | 8c / 16Gi | 4000m / 8000m | 8Gi / 16Gi | 160Gi |

用户**不需要知道**这些数字，只需要选档位。

## 8. 关键设计原则

1. **零术语**：界面中不出现任何 K8s/Docker 术语
2. **三步以内**：创建实例不超过 3 次点击
3. **自动默认**：能自动决定的都自动决定（镜像版本、Namespace、副本数）
4. **渐进披露**：先给最简结果，需要时再展开细节
5. **及时反馈**：每个操作都有明确的状态反馈

## 9. 与 PRD 的关系

本方案对应 PRD 中 **M3 里程碑**的"权限控制"需求：

> M3: 管理员 vs 普通用户；普通用户只能管理自己创建的实例，不能操作集群配置。

User Portal 本质上就是"普通用户视图"的独立实现，而非在 Admin Panel 中做权限裁剪。这种方式更彻底、体验更好。
